# Experiment 1: Capsule なし vs Capsule あり

**Date**: 2026-07-29  
**Type**: Proxy experiment (実LLM APIは未使用)  
**Script**: `examples/experiment1_capsule_llm_proxy.py`  
**DCK**: v0.9

---

## 1. 実験設計

### 条件

| 条件 | パイプライン | 説明 |
|------|--------------|------|
| **A** | LLM → DCK | Capsuleなし。PLP平滑化後の状態を直接DCKへ流す |
| **B** | LLM → Capsule → DCK | Capsuleが「維持すべき状態」方向へ観測値を引き寄せてからDCKへ |

### 評価指標（proxy）

| 指標 | 定義 |
|------|------|
| token数相当 (`token_proxy`) | 累積 gap × 120（探索量の代理） |
| tool call数 | Executor 呼び出し回数 |
| 修正回数 | `EXECUTE_CONVERGENCE` が選択された回数 |
| 最終品質 | 平均 gap（小さいほど目標に近い = 品質が高い） |
| 推論時間 | 壁時計時間（参考値） |
| T3_gap | 話題が大きく逸脱した Turn 3 の gap |

> **注意**: 本実験は実LLMを呼び出していません。  
> Capsule が差異をどう削減するかを、既存のDCKスタック上で定量的に観察する proxy 実験です。  
> 実LLM接続時は token / latency / 自己修正回数を直接計測する予定です。

## 2. 結果

```text
Metric                   A (no Capsule)   B (with Capsule)          Δ
----------------------------------------------------------------------
token_proxy                       330.7              164.1     -166.6
tool_call (executor)                 10                 10         +0
correction (EXEC)                    10                 10         +0
final_quality (avg gap)            0.276              0.137     -0.139
wall_time_sec                     0.013              0.005     -0.008
T3_gap (max drift)                0.755              0.352     -0.402
capital_remaining                997.24             998.63      +1.39
----------------------------------------------------------------------
```

### 数値まとめ

| 指標 | A (Capsuleなし) | B (Capsuleあり) | 変化率 |
|------|-----------------|-----------------|--------|
| token_proxy（探索量） | 330.7 | **164.1** | **-50%** |
| 平均 gap（最終品質） | 0.276 | **0.137** | **-50%** |
| Turn3 gap（最大逸脱） | 0.755 | **0.352** | **-53%** |
| リソース残 | 997.24 | **998.63** | 消費約半分 |
| tool call / 修正回数 | 10 | 10 | 変化なし* |

\* 現状の Decision 閾値では両方とも毎ターン EXEC が発火している。  
  閾値を厳しくすれば Capsule 側で NO_ACTION が増える可能性が高い。

---

## 3. 解釈

### Capsule の効果

- **探索量（token_proxy）が約半分**になった。
- 特に「話題が一時的に広がった Turn 3」での gap が大きく抑えられている。
- 最終的な平均 gap も半減 → 目標状態により近いところで制御できている。
- リソース消費も比例して減少。

これは Capsule が単なる「過去の記憶」ではなく、

> 「この状態を維持する必要がある」という**制約**

として機能し、DCK に届く差異を事前に削っていることを示している。

### LLM 本体比較としての意味

本実験は proxy だが、示唆は明確：

- Capsule なし → DCK は大きな差異を毎ターン検出し、大きな修正を繰り返す
- Capsule あり → 差異が小さくなり、DCK の仕事量が減る

実LLMを載せた場合、この「仕事量の減少」は  
**生成トークン数・自己修正回数・tool call の減少**として現れる可能性が高い。

## 4. 次のステップ（実LLM接続時）

1. Observer / Predictor / Executor を実際の LLM（Grok 等）に差し替える
2. 同じ会話シナリオで token 使用量・自己修正回数・最終応答品質を直接計測
3. Capsule の pull 強度をスイープして、探索削減と品質のトレードオフを取る

## 6. 結論（現時点）

Capsule を挟むだけで、DCK が扱う差異が約 50% 削減された。  
「LLMの自由探索を減らしつつ、制御品質を落とさない」方向の効果が、proxy レベルでは確認できた。

DCK の立ち位置は「AIを賢くする装置」ではなく、  
**AIの知能を効率的に使うための制御系** として説明可能な状態に近づいている。
